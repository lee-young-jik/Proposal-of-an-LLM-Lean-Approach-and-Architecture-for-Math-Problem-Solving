단계별 중간 명제 전략 비교 — 2026-10-18

결론
이번 변경은 채택하지 않는다. 새로 실행한 대조군은 Single0/2·Dual2/2, 단계형 조건은 Single0/2·Dual0/2였다. 원래 공통 goal_prompts.py를 실험 전 바이트로 복원했고, 단계형 조건은 실험 사본으로 보존했다. 이2문제1회 비교는 일반적인 악화의 통계적 증명이 아니지만, 현재 변경을 기본 설정으로 채택할 개선 근거는 없다.

실험 조건
이전 balanced22에서 Dual만 성공했던 노름 linear_algebra_6A_24와 불연속 calculus_23_3_7을 사용했다. 과거 결과만 비교 기준으로 삼지 않고 기존/단계형 각각 Single/Dual을 새로 실행해 총8회 비교했다. Single최대9시도, Dual각경로최대9시도(총18)인3라운드×3시도 조건을 유지했다. 전체 계산량을 동일하게 맞춘 실험은 아니다. 모델 LunaPro planner/Luna workers와 제공자, 독립 Natural, 메모리, Lean 환경 지원, Repair→Generator 구조는 동일했다. 공개 문제/고정 목표만 모델에 전달했고 이2문제의 정답 코드·사후 수동 수정은 입력하지 않았다.
실행은 조건별로 격리한 소스 패키지에서 수행했다. 각 실행의 실제 소스 사본과 지침 원문은 audit에 남겼다. 두 조건은 병렬 진행됐고 Lean은 공유 직렬 검증이므로 경과 시간을 아키텍처 고유 지연 비교로 해석하지 않는다.

정확한 변경 범위
단계형 조건은 공통 Planner/Generator/Repair 세 곳의 지침 묶음 변경이다. Orchestrator는 S1,S2…로 정의·증인·중간 명제·타입·선행 단계와 최종 종결을 쓰게 했다. Generator에는 타당한 단계의 중간 명제를 로컬 정의/have로 구현하고 해당 단계 주석을 남기게 했다. Repair에는 오류에 해당하는 단계 번호와 최소 Before/After 수정을 제시하게 했다. Natural 지침과 모델/메모리 구조는 변경하지 않았다.
따라서 관측 차이를 Orchestrator의 번호 형식 하나의 효과로 분리할 수는 없다. 단계형 구현 지침 묶음 전체에 대한 비교다.

형식과 실제 구현
단계형 Planner18개 출력 모두 S번호를 포함했다. 단계 번호가 코드에 등장한 trial은25/53, Repair 지침에 등장한 응답은38/53이었다. 여기에는 양방향의 실패 시도도 포함돼 있다. 이 비율은 형식 지표이며 논증의 타당성이나 의미상 전략 이행 성공률이 아니다. 단계 번호가 없어도 해당 중간 명제가 have로 구현된 경우가 있으므로 주석 유무로 의미상 준수를 판정하지 않는다.

노름 문제의 실제 차이
기존 Dual은 R1T2에 성공했다. 기존 전략도 기저벡터, 합/차 벡터, 제곱근 등식, 쌍선형 전개라는 중간 단계를 갖고 있었다. 정확히 타입을 지정한 제곱근 제곱 등식과 simp 기반 전개가 커널 검증됐다. 번호 추가가 없으면 중간 명제를 만들지 못하는 구조는 아니었다.
단계형 Dual의 R1 전략은 같은 네 벡터 논증을 S1~S5로 나눴고 Generator도 정의와 중간 등식을 구현했다. Repair는 S4 전개를 정확히 위치시켰으나 R1T1 응답에 동일한 Before/After를 제시한 뒤 확정할 수 없는 API를 설명하는 문제가 있었다. 번호를 찾은 것이 유효한 수정 코드를 보장하지 않았다.
R3에는 바깥/안쪽 덧셈·뺄셈을 각각 보조명제로 분리하는 실제 전략 개선이 있었다. 마지막 Repair의 제거/등식 방향 수정은 Generator가 반영했다. 하지만 hout_sub 증명 `rw [sub_eq_add_neg, hout_add]; simp` 뒤에 `B x z + -(B y z) = B x z - B y z` 목표가 남아 전체 검증에 실패했다. 오류 위치는 명확해졌지만 형식화 오류 회수에는 충분하지 않았다.
단계형 Single도 전개를 두 명제로 나눴으나 최종 change가 B의 선형성에 따른 등식을 정의적 동등성으로 취급해 실패했다.

불연속 문제의 실제 차이
기존 Dual은 수평축의 점(r,0)을 택해 값0과 원점값1이 연속성의 ε=1/2 조건에 모순된다는 더 단순한 metric 전략으로 R2T2 성공했다.
단계형 Dual은 R1/R2에 대각선 경로와 sin(t)/t 극한을 택했다. 그 과정에서 일반 원점 근방에서 sin(t)/t→1이라는 잘못된 형태를 계획에 적었고, 없는 Real.tendsto_sin_div API도 추정했다. 원점에서 sin(0)/0은 Lean의 실수 나눗셈에서0이므로 이 형태는 punctured filter나 수정한 원점값 없이 성립하지 않는다. 이후 R3에는 수평축의 역수 수열로 바꿨지만 잘못된 reciprocal-limit 정리 인자와 prod_mk API 오류가 남았다.
최종 Repair는 S2가 병목임을 짚었지만 확정된 대체 호출을 제시하지 못했고, Generator 최종 코드에는 `Membership ℝ (Filter ...)` 인스턴스 오류와 없는 `Function.prod_mk`가 남았다. 전략이 번호화돼도 추정한 API와 수학적 필터 조건이 정확해지는 것은 아니었다.
단계형 Single은 마지막까지 대각선 논증을 유지했고 도함수 기반 극한의 eventual equality 전달과 불필요한 tactic에서 실패했다. 기존 Single은 R1/R2에 올바른 disprove를 선택하다 R3에 prove로 바뀌었고, 단계형 Single은 세 라운드 모두 disprove를 유지했지만 둘 다 미해결이었다. 이것을 같은 실패 원인의 단순 전후 비교로 취급하지 않는다.

해석
계획을 번호로 나누고 중간 명제를 명시하는 행동 변화는 관찰됐다. 일부 라운드에서는 실패한 전개를 보조명제로 더 세밀하게 나누는 변화도 있었다. 그러나 정확한 증명 구성, 실제 Lean API, 필터 타입, Repair의 유효한 수정까지 자동으로 보장하지 않았다. 성공 수 개선은 없었고 이 소규모 비교에서는 Dual의 성공2개를 잃었다. 모델 생성 변동과 세 지침의 묶음 변경이 있어 보편적 인과 결론은 내리지 않는다.
추가 지침을 붙여 같은 두 문제에서 다시 성능을 맞추는 실험은 하지 않았다. 기존22문제 성적 Single15/Dual16도 변경하지 않는다.

검증과 기록
8개 root run 모두 LangSmith API에서 존재·완료·root error 없음 확인. 공통 핵심 지침의 구조 간 동등성, Natural 불변, 고정 목표, 소스 사본 해시, 예산, Planner 메모리에 Repair/오류 미포함을 감사했다. 한 번의 worker 출력 거부는 해당 시도에서만 처리됐고 전체 실행 오류는0이었다.
초기 단계형 프로세스는 LangSmith 프로젝트 동시 생성409 충돌로 모델 실행 전에 종료됐다. 같은 소스와 입력으로 기존 프로젝트를 읽도록 실행 준비 코드를 고쳐 시작했다. 원래 설정 실패 로그를 보존했으며 유료 문제 실행을 중복하거나 성적에서 제외한 것은 아니다.
