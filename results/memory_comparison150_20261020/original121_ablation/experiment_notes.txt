Orchestrator 라운드 간 기록 제거 어블레이션 (2026-10-19)

질문: 이전 실패 라운드의 전략·자연어 추론·Lean 코드를 보고 전략을 수정하는 것이 도움이 되는가?

기존 비교군: results/test121_final_20261019, 전체 121문제, Single 78/121, Dual 80/121.
새 조건: 동일 121문제에 Single/Dual 각 1회, 합계 242회 새 실행.
모델: Orchestrator openai/gpt-6-luna-pro, Natural/Generator/Repair openai/gpt-6-luna.
최대 예산: Single 3라운드 × 3시도 = 9회, Dual 경로별 동일 예산으로 양쪽 합계 18회.

유일한 입력 개입은 Orchestrator의 trial_memory를 매 라운드 비우는 것이다.
Single은 자기 이전 라운드 기록을 받지 않는다.
Dual은 자기 경로와 반대 경로의 이전 라운드 기록 모두 받지 않는다.
Natural은 기존처럼 독립 추론한다.
같은 라운드에서 Generator가 받는 이전 코드·오류·Repair 지침은 유지한다.
실행 로그에는 이전 시도를 보존하지만 Orchestrator 모델 입력으로 보내지 않는다.
기본 최종 구조나 .env를 바꾸지 않고 별도 frozen_runtime을 사용한다.

기존 memory_condition=none 옵션은 시스템 지침도 일부 변경한다.
이번에는 입력 기록의 효과를 구분하기 위해 별도 frozen_runtime의 goal_search.py에서
use_memory=True로 시스템 지침 선택을 고정했다. trial_memory 입력은 기존 조건 분기를 통해
none에서 비워진다. 다른 핵심 파일 11개는 기존 기준과 바이트 단위로 동일하다.
기록을 언급하는 기존 지침도 그대로 두는 '입력 제거' 실험이며,
기록 없는 시스템에 맞춘 최적 프롬프트의 성능을 측정하는 실험은 아니다.

유료 호출 전 실제 Planner 코드 18회 점검:
- 모든 라운드의 시스템 지침 동일.
- 첫 라운드 입력 동일.
- 2·3라운드는 trial_memory만 다름.
유료 실행 후에는 각 Orchestrator 입력이 비었는지, 실제 지침이 기존 로그와 일치하는지,
모델·제공자·토큰 상한·고정 목표·소스 해시·비공개 정답 미사용을 감사한다.

분석은 전체 성공률·비용·Lean 검증 횟수와 문제별 성공 변화를 비교한다.
두 조건 모두 첫 라운드 후 계속한 문제의 성적은 별도로 표시한다.
각 구조에서 기록 있을 때만/없을 때만 성공한 문제와 탐색적 paired 통계를 제공한다.

해석 한계:
- 기존 기록 있음 실행과 새 기록 없음 실행의 모델 출력을 첫 라운드부터 공유/재생하지 않는다.
  첫 라운드 입력은 같아도 샘플링에 의해 성공/실패가 달라질 수 있으며, 이를 기록 효과로 부르지 않는다.
- 두 조건 모두 첫 라운드 후 계속한 부분집합도 실패한 첫 라운드 내용은 서로 다르다.
- Dual은 자기/반대 기록을 동시에 제거하므로 반대 경로 공유만의 효과는 분리하지 않는다.
- 문제별 조건별 1회이며, 이미 살펴본 개발 문제도 포함한 데이터 전체 평가다.
- 분야/연습문제 간 의존성과 공급자 실행 시점 차이가 있을 수 있다.
- 성공은 제공된 Lean 형식 목표에 대한 검증이다.
